# 05-knowledge (Project Knowledge Base & Field Learnings)

본 디렉토리는 시스템의 개발, 검증, 운영 과정에서 습득된 **실질적인 기술 지식, 트러블슈팅 이력, 런타임 교훈(Lessons Learned)**을 축적하는 공간입니다.

> **운영 핵심 원칙:**  
> "지금 목표는 이론적 백과사전을 만드는 게 아니라, 실제 작업 중 맞닥뜨린 문제와 해결책을 신속히 찾아볼 수 있게 하는 것입니다."  
> 문서 작성을 위한 문서는 지양하며, 실질적인 이슈 해결이나 도메인 특이점이 발생할 때 온디맨드(On-demand)로 문서를 작성합니다.

---

## 1. 문서 계층 간 책임 경계 (Separation of Concerns)

`05-knowledge`는 타 문서 계층과 다음과 같이 명확히 역할을 분리합니다:

| 문서 계층 | 주요 질문 | 다루는 내용 | 05-knowledge와의 차이점 |
| :--- | :---: | :--- | :--- |
| **`01-prd`** | WHAT | 기능/비기능 요구사항, 보안 스펙, 인수 기준 (AC) | 비즈니스/보안 목표를 정의하며, 구현 디버깅을 다루지 않음 |
| **`02-architecture`** | WHERE | 시스템 토폴로지, 데이터 흐름, 컴포넌트 구조 | 전체 설계도를 다루며, 특정 라이브러리의 엣지 케이스는 다루지 않음 |
| **`03-adr`** | WHY | 기술적 의사결정 이유, 비교 대안, 트레이드오프 | "왜 선택했는가"를 기록하며, 구현 중 발생한 런타임 버그는 다루지 않음 |
| **`04-task-progress`** | HOW / WHEN | 우선순위(P0~P2) 기반 실행 TASK, 검증 추적성 | 진행 상태와 Evidence를 다루며, 재사용 가능한 기술 지식은 분리 |
| **`05-knowledge`** | **LEARNING** | **트러블슈팅, 장애 원인/해결, 기술 라이브러리 팁, 도메인 사전** | **실제 엔지니어링 과정에서 얻은 지식과 노하우의 단일 저장소** |
| **`06-ai-engineering`** | AI-FLOW | AI 프롬프트 규약, AI 제안 실패 및 반박 사례 | AI 협업 프로세스에 특화된 기록 |
| **`07-operations`** | RUN-OPS | 환경 설정(.env), 배포/기동 가이드, 모니터링 운영 | 시스템 기동/운영 절차 가이드 |
| **`conventions`** | STANDARDS | 코딩 표준, DTO/Entity 분리, 공통 응답 규격 | 코드 작성 시 준수해야 할 강제 규약 |
| **`changelog`** | HISTORY | 과거 작업 스냅샷 및 릴리즈 이력 | 과거 이력 보존 (읽기 전용) |

## 2. 수록 대상 및 가이드라인

### 1) 포함 대상 (In-Scope)
* **트러블슈팅 및 장애 복기:** 개발/테스트 중 발생한 예외, 원인 분석, 해결책 및 재발 방지책
* **기술적 주의사항 및 라이브러리 팁:** Spring Boot, JPA, Redis, React, Vite 등 도구의 특이 동작이나 제약 극복법
* **도메인 기술 레퍼런스:** 프로젝트 특화된 인증/인가 메커니즘 해석 및 실무 가이드

### 2) 배제 대상 (Out-of-Scope)
* 코딩 컨벤션 및 표준 서식 ➔ `conventions/`에 위치
* 아키텍처 다이어그램 및 시퀀스 흐름도 ➔ `02-architecture/`에 위치
* 설계 결정 근거 ➔ `03-adr/`에 위치
* 내용 없는 0바이트 빈 파일이나 사전 폴더 트리 생성 금지

## 3. 표준 트러블슈팅 문서 작성 템플릿

새로운 문제 해결 기록을 남길 때는 아래 규격을 따릅니다:

```markdown
# [Troubleshooting] {이슈 제목}

- **일자:** YYYY-MM-DD
- **영역:** Backend / Frontend / Redis / MySQL / Security
- **관련 커밋/TASK:** {TASK-ID 또는 Commit Hash}

### 1. Symptoms (증상)
* 어떤 에러나 비정상 동작이 관측되었는가? (로그, HTTP 상태 코드 등)

### 2. Impact (영향도)
* 이 이슈가 시스템 기능이나 보안, 데이터 정합성에 미친 영향

### 3. Root Cause (근본 원인)
* 문제의 기술적 원인 분석 (코드 결함, 동시성 레이스, 라이브러리 동작 오해 등)

### 4. Resolution (해결 조치)
* 실제 수정/적용된 코드나 인프라 설정 내용

### 5. Prevention (재발 방지)
* 동일 이슈 방지를 위한 규칙, 자동화 테스트, 모니터링 알림 추가 내용
```
