**Related PRD:** PRD-SEC-001-jwt

## 1. Context & Drivers

APMS.SR 시스템은 React 기반의 Frontend와 Spring Boot 기반의 Backend가 분리된 구조(`ADR-0001`)를 가지며, 이들 간의 안전한 API 통신을 위해 인증 상태를 식별하고 인가(Authorization)를 수행할 수 있는 메커니즘이 필요하다.

매 API 요청마다 MySQL에서 사용자 및 권한 정보를 조회하는 것은 성능 병목을 유발할 수 있으므로, 인증 토큰 자체에 필요한 최소한의 정보를 담아 Stateless하게 검증할 수 있는 수단이 요구된다. 

본 결정의 주요 판단 기준은 다음과 같다.

1. API 요청에 대한 인증 및 인가 처리 성능 (Stateless 검증)
2. Frontend와 Backend 간의 결합도 최소화
3. 단일 Backend Application 구조에 적합한 암호화 및 서명 방식
4. 탈취 위험을 최소화하기 위한 토큰 생명주기 및 Payload 크기
5. 현재 시스템 규모에 적합한 운영 및 관리 단순성

## 2. Options Considered

### Option A — Server-side Session (JSESSIONID)

Spring Security의 기본 방식인 서버 사이드 세션을 사용하고, Redis를 통해 세션을 공유(Spring Session)한다.

**Advantages**
* 토큰 탈취 시 서버 측에서 세션을 즉각적으로 만료(Invalidation)시킬 수 있다.
* 구현이 매우 직관적이며 기존 레거시 시스템과의 호환성이 높다.

**Disadvantages**
* Frontend(React)와 Backend가 강하게 결합되며, CSRF 방어를 위한 추가 설정이 복잡하다.
* 모든 API 요청 시마다 Session Store(Redis)를 필수적으로 조회해야 하므로 오버헤드가 발생한다.

---

### Option B — Symmetric Key JWT (HS256)

대칭키 암호화 알고리즘(HMAC SHA-256)을 사용하여 JWT를 서명하고 발급 및 검증한다.

**Advantages**
* 단일 서버 또는 동일한 Secret Key를 공유하는 환경에서 서명 및 검증 속도가 매우 빠르다.
* 서버 메모리나 외부 저장소(Redis/MySQL)를 조회하지 않고도 토큰의 유효성과 권한(Claims)을 즉각적으로 확인할 수 있다.
* 구조가 단순하여 구현 및 관리가 용이하다.

**Disadvantages**
* Secret Key가 유출될 경우 시스템 전체의 인증이 뚫리는 치명적인 보안 결함이 발생한다.
* Access Token 자체를 만료 시간 전에 강제로 무효화하기 어렵다.

---

### Option C — Asymmetric Key JWT (RS256)

비대칭키 암호화 알고리즘(RSA SHA-256)을 사용하여 인증 서버(Private Key)가 토큰을 발급하고, API 서버들(Public Key)이 검증한다.

**Advantages**
* Microservices Architecture(MSA) 환경에서 서비스 간 키 공유 없이 안전하게 토큰을 검증할 수 있다.

**Disadvantages**
* 대칭키 방식에 비해 서명 및 검증 시 컴퓨팅 자원(CPU) 소모가 더 크다.
* Key Pair(Private/Public Key)의 생성, 보관, 교체(Rotation)를 위한 추가 인프라(Key Management)가 필요하다.
* 단일 Backend Application(`ADR-0001`) 구조에서는 불필요한 오버엔지니어링이다.

---

## 3. Decision

현재 시스템의 API 인증 및 인가 매개체로
 — Symmetric Key JWT (HS256)를 채택한다.

Frontend와 Backend 간의 API 통신에서 Access Token으로 JWT를 사용한다.

Access Token의 서명, 만료 시간 및 기본 Claim 검증은
서버 측 상태 저장소에 의존하지 않고 Stateless하게 수행한다.

JWT에는 사용자 식별자와 인증에 필요한 최소한의 Claim만 포함한다.

Access Token의 즉각적인 무효화가 필요한 경우에는
ADR-0003에서 결정한 Redis 기반 Token Invalidation 정책을 적용한다.

현재 시스템은 단일 Backend Application 구조이므로
별도의 공개키 배포가 필요한 RS256 대신 HS256을 사용한다.

---

## 4. Rationale

### 4.1 Stateless Access Token Validation

* Access Token의 기본적인 유효성 검증은
JWT Signature와 Expiration 및 Claim 검증을 통해 수행한다.

* 이 과정은 사용자별 Session State에 의존하지 않으므로
기본적인 Access Token 검증을 Stateless하게 처리할 수 있다.

* 다만, Token Blacklist와 같은 즉각적인 무효화 정책은
Redis 기반의 별도 상태를 사용하며,
이는 ADR-0003에서 정의한 Authentication State 관리 영역에 해당한다.

### 4.2 Suitable for Monolithic Layered Architecture
단일 Application 내에서 토큰을 발급하고 동일한 Application이 토큰을 검증하므로, 공개키를 외부에 배포해야 하는 비대칭키 구조는 필요하지 않다. 대칭키 방식은 보안성을 유지하면서도 연산 비용을 최소화한다.

### 4.3 Payload Optimization (Claims)

JWT 내부에는 사용자 식별 및 인증에 필요한 최소한의 Claim만 포함한다.

불필요한 사용자 정보나 상세 권한 정보를 Token Payload에 포함하지 않으며,
실시간 권한 검증이 필요한 경우에는 별도의 Authorization 정책에 따라
서버 측 권한 정보를 조회할 수 있다.

이를 통해 JWT의 크기를 최소화하고 권한 변경 시 기존 Token과
서버 측 권한 정보 간의 불일치 범위를 줄인다.

## 5. Consequences

### Positive

#### 낮은 서버 부하
Access Token 검증 과정에서 DB나 Redis 조회가 발생하지 않아(Blacklist 검증 제외) 대용량 트래픽 처리에 유리하다.

#### 확장성 및 독립성
Frontend 앱(웹, 모바일 등)의 종류에 구애받지 않고 Authorization Header를 통해 유연하게 통신할 수 있다.

---

### Negative

#### 실시간 권한 반영의 지연
사용자의 권한(Role)이 MySQL에서 변경되더라도, 이미 발급된 JWT Access Token이 만료되기 전까지는 변경된 권한이 반영되지 않는 취약 시간(Window)이 존재한다.

#### Secret Key 관리 부담
대칭키 유출을 막기 위해 소스 코드가 아닌 외부 환경 변수(Environment Variable)나 시크릿 매니저를 통해 안전하게 주입하고 관리해야 하는 운영 요구사항이 발생한다.

---

## 6. Verification

본 ADR의 결정은 다음 항목을 실제 실행을 통해 검증한다.

### 6.1 Token Signature & Validation
* 변조된 서명(Invalid Signature)을 가진 토큰으로 요청 시 `JwtAuthenticationFilter`에서 즉각적으로 예외(401 Unauthorized)가 발생하는지 확인한다.

### 6.2 Expiration (TTL)
* 만료 시간이 지난 Access Token 사용 시 토큰이 정상적으로 거부되는지 확인한다.

### 6.3 Claims Parsing
* JWT Payload에서 추출한 사용자 ID와 Authority 정보를 바탕으로 Spring Security Context가 정상적으로 구성되는지 확인한다.

### 6.4 Algorithm Validation

* 허용되지 않은 JWT Algorithm을 사용하는 토큰이 거부되는지 확인한다.
* HS256으로 발급된 토큰의 Signature가 정상적으로 검증되는지 확인한다.
* 잘못된 Secret Key로 생성된 토큰이 거부되는지 확인한다.

## 7. Conditions for Reconsideration

다음과 같은 상황이 실제 측정 또는 운영 결과로 확인되면 본 결정을 재검토한다.

### 7.1 Architecture Shift to Microservices
시스템 확장에 따라 여러 개의 독립적인 서비스가 API 인증을 개별적으로 검증해야 하는 경우 (비대칭키 RS256 방식으로 전환 필요).

### 7.2 Strict Real-time Authorization

권한 변경 또는 권한 박탈을 Access Token의 만료 시점까지
기다릴 수 없는 수준의 실시간 Authorization 요구사항이
발생하는 경우.

이 경우 서버 측 인증 상태 조회 또는 별도의
Authorization 검증 구조를 검토하고 새로운 ADR을 생성한다.

### 7.3 Payload Size Bottleneck
토큰 내부에 포함해야 하는 Claim 데이터가 과도하게 증가하여 Network Bandwidth 및 HTTP Header Size 제한에 병목을 일으키는 경우.

## 10. Decision Summary

> APMS.SR은 Frontend와 Backend 간의 Stateless 인증 처리를 위해 **Symmetric Key 기반의 JWT (HS256)** 를 채택한다.
> 
> 데이터베이스(MySQL) 조회 부하를 줄이기 위해 JWT 내부에 사용자 식별자와 핵심 권한(Claims)을 포함시키며, 단일 Backend 구조이므로 연산이 빠르고 관리가 단순한 대칭키 방식을 사용한다.
> 
> JWT의 단점인 실시간 권한 제어 불가 및 탈취 위험은 Token의 유효 기간(TTL)을 짧게 설정하고, Redis 기반의 Refresh Token/Blacklist와 결합하여 보완한다.
> 
> 향후 Microservices로의 전환이 발생하거나 실시간 권한 반영이
  필수적인 보안 제약이 추가될 경우, 새로운 ADR을 통해 
  JWT 알고리즘 및 인증 구조 및 인증 구조를 재검토한다.
